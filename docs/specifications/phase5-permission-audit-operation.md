# Phase 5：権限・監査・運用仕様

（編集者限定 / 変更履歴 / 棚卸 / 安全な運用）

## 1. このフェーズの目的

本フェーズの目的は、
**「全社員が閲覧でき、編集は限定された管理者のみが行える」**という運用要件を、
システム仕様として明文化し、長期運用（1〜5年）に耐える状態にすること。

- 認証（ログイン）と認可（編集可否）を分離して設計する
- 誤操作・誤設定を前提に「復旧できる」仕組みを用意する
- 変更履歴（監査）と棚卸（腐敗防止）を最初から組み込む

---

## 2. ロール（役割）定義

本プロジェクトは最低限、以下のロールを持つ。

### 2.1 Viewer（閲覧者）

| 項目 | 内容 |
|------|------|
| 対象 | 全社員 |
| 権限 | ポータル閲覧、link/埋め込みの利用、ページ切替 |
| 禁止 | 編集モードへの遷移、ウィジェット/ページの変更 |

### 2.2 Editor（編集者）

| 項目 | 内容 |
|------|------|
| 対象 | 本人＋総務の一部管理者 |
| 権限 | 編集モードの利用（配置変更、リサイズ、ページ追加など）、スプレッドシート（設計DB）の更新 |
| 禁止（初期） | 監査ログ削除、権限設定の勝手な変更（Adminのみ） |

### 2.3 Admin（管理者：任意）

| 項目 | 内容 |
|------|------|
| 対象 | 最小人数（本人） |
| 権限 | Editorの追加・削除、監査・棚卸設定の管理 |

※ 初期は Editor と同一でもよいが、将来のため概念は残す

---

## 3. 認証（Authentication）

### 3.1 前提

- Google Workspace でのログインを前提とする
- ポータルは「ログインしないと見られない」運用を基本とする
  （社内公開要件がある場合のみ例外）

### 3.2 仕様（要求）

- 未ログインユーザーはログインへ誘導
- ログイン後、ユーザー識別子（メール等）を取得できること

---

## 4. 認可（Authorization）

### 4.1 編集者判定

以下いずれかの方式を採用（実装都合で選択）：

| 方式 | 内容 | 推奨 |
|------|------|------|
| 方式A | **編集者リストをスプレッドシートで管理** - 例：`07_権限` シート（将来追加）、editor_emails に本人＋総務のメール | ✅ 推奨 |
| 方式B | 環境変数/設定ファイルで管理（初期運用向け） | 初期MVP可 |

※ 初期MVPでは方式Bでも良いが、長期運用は方式Aが望ましい。

### 4.2 UI上の制御

- Viewerには編集導線を表示しない
- `/admin` への直アクセスは拒否し、403/権限なし画面へ

---

## 5. スプレッドシート更新権限（運用の要）

### 5.1 原則

- スプレッドシート（設計DB）は **編集者のみ編集可能**
- 一般社員には閲覧権限を付与しない（原則）

### 5.2 実装上の注意

- Sheets API を使う場合も、更新系APIはサーバ側で行い、
  クライアントからは「編集者のみ呼べる」よう制御する

---

## 6. 監査ログ（変更履歴）

### 6.1 目的

- 誰が・いつ・何を変更したかを追える
- 誤操作があっても復旧できる

### 6.2 最小ログ要件（MVP）

最低限、以下を記録する：

| 列名 | 説明 |
|------|------|
| timestamp | 変更日時 |
| actor | 変更者（メール/ID） |
| target | ページID / ウィジェットID |
| action | create / update / delete / restore |
| before | 変更前の主要データ（JSON等） |
| after | 変更後の主要データ（JSON等） |

### 6.3 保存先

| 方式 | 内容 | 推奨 |
|------|------|------|
| 方式A | スプレッドシートに `08_監査ログ` シートを追加 | ✅ 初期推奨 |
| 方式B | 別DB（Firestore等）へ保存 | 将来拡張 |

※ 初期は方式Aで十分。

### 6.4 ロールバック（復旧）

- 監査ログの「before」を使って復旧できることが望ましい
- 初期は手動復旧でもよいが、ログは必ず残す

---

## 7. 棚卸（Review Cycle / 腐敗防止）

### 7.1 目的

ポータルは放置するとリンク切れ・情報陳腐化が起きるため、
棚卸を運用設計に組み込む。

### 7.2 データ（既存列）

| 列 | 値 |
|----|-----|
| 02_ウィジェット.review_cycle | monthly / quarterly / semiannual / annual / none |
| 02_ウィジェット.owner | 管理者（責任者） |

### 7.3 棚卸の最小運用（MVP）

- 管理画面に「棚卸対象一覧」を表示
  - review_cycleに応じて「期限切れ/期限近い」を判定
- 初期はメール通知等は不要（将来拡張）

---

## 8. 誤操作対策（必須）

### 8.1 破壊的操作の確認

以下の操作には確認ダイアログを必須とする：

- ページ削除
- ウィジェット削除
- 大量変更の保存

### 8.2 ソフトデリート（推奨）

- 「削除」は物理削除ではなく `visible=FALSE` へ変更し非表示にする
- 監査ログとセットで復旧しやすくする

---

## 9. 競合（同時編集）

### 9.1 初期方針

- 初期MVPでは「同時編集は原則しない」前提でも良い

### 9.2 最低限の衝突対策（推奨）

- 保存時に `updated_at` 的な値（または最終更新行）を確認し、
  競合が疑われる場合は警告する（将来拡張）

---

## 10. 情報セキュリティ（補足）

### 10.1 HTML/Markdownの扱い

| 形式 | 推奨度 | 備考 |
|------|--------|------|
| markdown | ✅ 推奨 | 安全、運用容易 |
| 生HTML | 限定利用 | XSSリスクあり、編集者を厳密に限定、サニタイズを検討 |

### 10.2 埋め込み（iframe）

- 埋め込みはセキュリティヘッダの制約を受ける
- フォールバック（link）を常に用意する（Phase4参照）

---

## 11. Phase 5 完了条件（Definition of Done）

- Viewer / Editor / Admin の権限範囲が明確
- 編集導線の表示/非表示と、直接アクセス拒否が仕様化
- 監査ログの最小要件が確定
- 棚卸（review_cycle）の運用が仕様化
- 誤操作対策（確認・ソフトデリート）が仕様化
